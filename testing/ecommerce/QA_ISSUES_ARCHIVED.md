### Issue E1-3: Olist adapter discards the real order_status column, mislabeling ~3% of orders
- **Description:** `flatten_olist_dataset()`'s output never carries over Olist's real `order_status` column, and never populates `refund_amount` either — so every Olist order ingested through this adapter falls through `_resolve_generic_status()`'s `refund_amount` check (always `None`→falsy) and is unconditionally assigned `OrderStatus.fulfilled`, regardless of its true status. Quantified: 2,963 of 99,441 real Olist orders (2.98%) have a real non-"delivered" status (625 canceled, 609 unavailable, 314 invoiced, 301 processing, 1,107 shipped, 5 created, 2 approved).
- **Severity:** Medium
- **Impact:** Every Olist order ingested via this adapter shows `status: fulfilled` even if it was really canceled/unavailable/etc. — a real data-fidelity loss.
- **Root cause:** The adapter's join/flatten step was scoped only to the 3 fields needed for GENERIC_COLUMN_MAP's happy path; order_status was never in scope.
- **Suggested fix:** Extend `flatten_olist_dataset()` to map Olist's `order_status` values onto `OrderStatus`, or pass a status hint through a currently-unused canonical field.
- **Blocks Prompt 2:** No — confirmed in Prompt 2 via real ingestion: every one of the 112,650 ingested Olist rows shows `status: "fulfilled"`, exactly as predicted.

### Issue E1-4: `ecommerce_orders_10k_updated.csv`'s gross_revenue/unit_price both resolve to the wrong column
- **Description:** This file has both a `price` (per-unit) and `total_price` (order total) column. `find_column`'s fuzzy fallback (used because this file has no literal `gross_revenue`/`unit_price` header) returns the FIRST column in dataframe order containing an amount-keyword — confirmed empirically via `find_column(df, COLUMN_CANDIDATES['amount'])` returning `'price'`, not `'total_price'`, since `price` appears earlier in the file's column order. Both `gross_revenue` and `unit_price` share the same `'amount'` fallback role, so **both** resolve to the same (wrong, for gross_revenue) column.
- **Severity:** High
- **Impact:** `Order.gross_revenue` is silently understated for every row where `qty > 1` (using the per-unit price instead of the true order total).
- **Root cause:** `_FALLBACK_ROLE` maps both `gross_revenue` and `unit_price` to the same `'amount'` role, and `_resolve_column`'s fuzzy fallback has no way to distinguish "order total" from "unit price" columns by name alone — it just takes the first match.
- **Suggested fix:** Give `gross_revenue` its own fallback role/keyword list biased toward "total"-style column names, distinct from `unit_price`'s.
- **Blocks Prompt 2:** No — confirmed in Prompt 2 via real ingestion: the sample order (order_id 100000, price=93.11, qty=2, total_price=186.22) was written with `gross_revenue=93.11`, exactly as predicted.

### Issue E1-5: `ecommerce_orders_10k_updated.csv` orders get a hardcoded NGN currency despite spanning 15 non-Nigerian countries
- **Description:** This file has no currency column at all; `write_canonical_rows`'s hardcoded fallback (`row["original_currency"] or "NGN"`) applies to every row, even though the file's own `country` column shows orders from Brazil, USA, Japan, Germany, etc. — never Nigeria.
- **Severity:** Medium
- **Impact:** Every order in this dataset is tagged with a currency that has no relationship to the order's real country of origin.
- **Root cause:** The ingestion code's hardcoded default currency ("NGN") was chosen for Scanwick's own primary market and applies unconditionally whenever a currency column is absent, regardless of dataset.
- **Suggested fix:** Consider deriving a currency default from `country` when present (this file has one), or exposing a per-ingestion-call default-currency parameter instead of a single hardcoded constant.
- **Blocks Prompt 2:** No — confirmed in Prompt 2 via real ingestion: all 10,000 ingested rows show `original_currency: "NGN"`.

### Issue E1-6: `archive (19)/orders.csv`'s "Cost Price Per Unit" column cannot currently be used as a COGS source, and this file would silently mis-map unit_price if ever ingested

## Newly Discovered Ecommerce Prompt 2 issues (Ingestion Testing)

### Issue E2-1: `net_margin` (order-level and item-level) silently omits `processing_fees` and `allocated_ad_spend`, overstating margin
- **Description:** `write_canonical_rows` (`app/services/ecommerce_ingestion.py:336-343` for the order-level call, `:317-323` for the item-level call) invokes `compute_net_margin(...)` **without** passing `processing_fees=` or `allocated_ad_spend=` at either call site — even though both fields are real, populated columns on `Order` (confirmed non-null for every row of `scanwick_test_ecommerce_orders.csv`, e.g. 360.00/736.00 for order 100001) and even though `compute_net_margin()`'s own function signature (`app/services/ecommerce_margins.py:5-38`) fully supports both parameters. Verified by independently recomputing `net_margin` for all 1,964 real ingested orders from this file (982 from a return_cost=0 ingestion pass, 982 from a return_cost=500×quantity ingestion pass): **0 of 1,964 mismatch** against the formula `gross_revenue − refund − discount − cogs − shipping − return_cost` (i.e., this is exactly, exclusively, what the code actually computes); **1,964 of 1,964 mismatch** against the full spec formula that would also subtract `processing_fees`/`allocated_ad_spend` (e.g., order 100001: stored `net_margin=2000.00`, full-formula recompute = `904.00`, a 1,096.00 difference exactly equal to `360.00+736.00`).
- **Severity:** High
- **Impact:** Every order's net margin — the platform's core profitability metric — is systematically overstated whenever `processing_fees` and/or `allocated_ad_spend` are non-zero, which is every row of the one dataset in this repository that actually populates those fields. This is not a data-quality issue; it is a call-site defect in `write_canonical_rows` (the two `compute_net_margin(...)` invocations are simply missing two keyword arguments the function already supports).
- **Root cause:** `write_canonical_rows`'s two `compute_net_margin(...)` calls omit `processing_fees=row.get("processing_fees")` and `allocated_ad_spend=row.get("allocated_ad_spend")`, despite both values already being available in the same `row` dict used for the `Order(...)` construction immediately above.
- **Suggested fix:** Add `processing_fees=row.get("processing_fees")` and `allocated_ad_spend=row.get("allocated_ad_spend")` to the order-level `compute_net_margin(...)` call. (The item-level `unit_net_margin` call has no per-item equivalent of these two fields in the schema at all, so whether it should include them is a separate design question — flagged for follow-up, not assumed.)
- **Blocks Prompt 3:** No — the miscalculation is systematic and consistent (not a crash, not row-dependent), so downstream dashboard/margin endpoints can still be tested meaningfully as long as this known discrepancy is kept in mind when interpreting any margin-derived figure.

### Issue E2-2: No duplicate-ingestion protection exists for Ecommerce (confirmed empirically)
- **Description:** Re-ingesting the identical `scanwick_test_ecommerce_orders.csv` file under the same `merchant_id` a second time created a full second set of 982 `Order` + 982 `OrderItem` rows (1,964 total of each after 2 ingestions), with zero deduplication, rejection, or merge logic observed. Confirmed via direct DB count before/after (982→1,964 for both tables) and by inspecting `write_canonical_rows`/the `orders`/`order_items` migrations for any unique constraint on `external_order_id`, `merchant_id`, or any content hash — none exists.
- **Severity:** High
- **Impact:** Re-uploading the same statement/export (an easy real-world user mistake) silently doubles a merchant's order history, corrupting every downstream dashboard/diagnostic/predictive/AI figure that aggregates over `orders`/`order_items` for that merchant.
- **Root cause:** No dedup mechanism designed or implemented anywhere in the Ecommerce ingestion path — the same class of gap already documented for Bank (`testing/bank/QA_ISSUES.md`'s B2-2), confirmed here independently for Ecommerce rather than assumed to also apply.
- **Suggested fix:** Add a content-hash or `(merchant_id, external_order_id)`-based uniqueness check before creating a new `Order` row.
- **Blocks Prompt 3:** No — but any dashboard/diagnostic figure computed for the merchant used in this duplicate test (`11111111-1111-1111-1111-111111111111`) will reflect double-counted data as a direct, expected consequence of this test, not a fresh defect to rediscover there.

### Issue E2-3: The `returns` table is never populated by any ingestion path — the return-forensics diagnostic is guaranteed to return empty results
- **Description:** Confirmed via grep across `app/services/ecommerce_ingestion.py` and `app/services/ecommerce_olist_adapter.py`: neither file ever constructs a `Return(...)` object or imports the `Return` model. Confirmed via direct DB query: the `returns` table has 0 rows after ingesting 125,796 real orders across 3 datasets (982+982+10,000+112,650) plus 2 pre-existing orphaned merchants' worth of data. Separately confirmed via reading `app/services/ecommerce_returns.py` (the `return-forensics` diagnostic's backing service): it reads FROM the `returns` table via a real `Order`-joined query (`_fetch_merchant_returns`, `:17-21`) — meaning this diagnostic feature currently has no possible data source and will return an empty result for every merchant in this repository, not because of any dataset gap, but because nothing anywhere writes to this table.
- **Severity:** High
- **Impact:** `return-forensics` (a real, implemented, migrated, route-exposed diagnostic — `GET /api/v1/ecommerce/diagnostic/return-forensics`) cannot produce any real output with any currently-ingestible dataset. `scanwick_test_ecommerce_orders.csv` even has real, well-formed return-related source columns (`returns_amount`, `refund_amount`, `return_carrier`, `return_reason` — the latter two already classified "Ignored" in Prompt 1's field mapping, referenced here rather than re-discovered) that would have been exactly the right data to populate this table, had a writer existed.
- **Root cause:** No ingestion code path anywhere constructs `Return` rows — an implementation gap between the `Return` model/migration (which exist) and the ingestion pipeline (which never uses them).
- **Suggested fix:** Add `Return` row construction to `write_canonical_rows` (or a parallel step) for sources that carry return-detail columns (e.g. `scanwick_test_ecommerce_orders.csv`'s `return_carrier`/`return_reason`/`returns_amount`), gated on `refund_amount > 0` similar to how `_resolve_generic_status` already uses that same signal for order status.
- **Blocks Prompt 4:** No — but Prompt 4 (Diagnostics Endpoint Testing) should expect `return-forensics` to return an empty/degenerate result for every dataset tested, and should treat that as this confirmed, pre-existing gap rather than a new diagnostic-layer defect.

### Issue E2-4: The COGS-missing quality-report warning gives no signal at all for datasets with zero SKU-bearing rows
- **Description:** `compute_ecommerce_quality_report`'s COGS-missing check (`app/services/ecommerce_ingestion.py:409-427`) computes `cogs_missing_pct` only over `line_items` (rows where `sku` is truthy) and only appends a warning `if total_line_items > 0`. For `ecommerce_orders_10k_updated.csv` (which has no `sku` column at all — 0 of 10,000 rows produce an `OrderItem`), `total_line_items` is 0, so the warning never fires — confirmed via real ingestion (`warnings: []`). By contrast, the Olist dataset (which DOES have `sku` for all 112,650 rows) correctly triggers the warning at exactly 100.0% missing, confirmed via direct function call to `compute_ecommerce_quality_report` on the flattened Olist rows.
- **Severity:** Low
- **Impact:** Not misleading (no false claim is made), but a consumer of the 10k file's quality report gets zero indication that COGS/margin data is completely absent for this dataset — the mechanism is a correct divide-by-zero guard, not a bug, but it means the one dataset most in need of a "no margin data available" signal (100% of rows lack it) is the one dataset that can never receive this specific warning.
- **Root cause:** The warning's denominator is scoped to "line items with a SKU," which is a reasonable definition in general but has this edge-case blind spot for SKU-less sources.
- **Suggested fix:** Consider a separate, order-level (not line-item-level) signal for "0 line items were created from this upload at all," independent of the COGS-specific warning.
- **Blocks Prompt 4:** No.

## Newly Discovered Ecommerce Prompt 4 issues (Diagnostics Endpoint Testing)

### Issue E4-1: `OrderItem.unit_return_cost` persists the raw, unresolved source value instead of the actual return cost used in its own margin calculation
- **Description:** In `write_canonical_rows` (`app/services/ecommerce_ingestion.py:308-334`), the local variable `unit_return_cost` is reassigned at line 308 to the *resolved* value from `resolve_unit_return_cost(row["unit_return_cost"], merchant_default_return_cost)` (correctly used at line 313 for `resolved_return_cost` and line 322 for the item-level `compute_net_margin(...)` call). However, the `item_fields` dict constructed at line 326-334 sets `unit_return_cost=row["unit_return_cost"]` (line 332) — re-reading the *original, pre-resolution* source-row value, not the local `unit_return_cost` variable that was just computed and actually used to derive `unit_net_margin`. Confirmed via direct SQL: 0 of 1,964 `order_items` for the primary merchant have a non-null `unit_return_cost`, even though 982 of them (the second Prompt-2 ingestion pass, after `MerchantSettings.default_return_cost=500` was configured) demonstrably had a real `500`-per-unit return cost applied — their `unit_net_margin` values are exactly `500 × quantity` lower than their first-pass counterparts (already observed, though not flagged as a distinct issue, in Prompt 2's own JSON output).
- **Severity:** High
- **Impact:** The persisted `OrderItem.unit_return_cost` column can never be trusted to reflect what was actually used to compute that row's own `unit_net_margin` — it always shows the raw source value (typically `None`) even when a real Merchant-Default (or, if ever exercised, SKU-Override) return cost was genuinely applied. This breaks any attempt to audit/reconcile a stored margin figure against its own displayed inputs, and would misinform any future feature or manual review that reads `unit_return_cost` directly (e.g., "this line item shows no return cost, so return cost isn't why its margin is negative" would be a false conclusion).
- **Root cause:** Variable shadowing/reuse bug — the same name (`unit_return_cost`) is used for both the pre-resolution source value (implicitly, via `row["unit_return_cost"]`) and the post-resolution value (the reassigned local variable), and the `item_fields` dict construction accidentally reaches back into the original `row` dict instead of using the local variable already in scope.
- **Suggested fix:** Change line 332 from `unit_return_cost=row["unit_return_cost"]` to `unit_return_cost=unit_return_cost` (the local, resolved variable already in scope) — or rename one of the two values to avoid the shadowing entirely.
- **Blocks Prompt 5:** No — the aggregate `net_margin`/`unit_net_margin` figures themselves are correct (confirmed in Prompt 2); only the separately-displayed `unit_return_cost` column is wrong.

### Issue E4-2: `profit-leaks`' `leak_breakdown`/`primary_leak_driver` omits COGS entirely and includes 4 of its 5 displayed components with zero causal connection to the actual margin formula
- **Description:** `compute_profit_leaks` (`app/services/ecommerce_diagnostics.py:56-71`) builds `leak_breakdown` from `order.refund_amount` (labeled `returns_cost`), `item.unit_shipping_cost` (labeled `shipping_cost`), `order.discount_amount` (labeled `discount_cost`), `order.processing_fees`, and `order.allocated_ad_spend`. But the `net_margin` value these are meant to explain (`item.unit_net_margin`, summed) is computed at ingestion time (`ecommerce_ingestion.py:317-323`) as `unit_price − unit_cogs − unit_shipping_cost − return_cost` — a formula that includes **only** `unit_cogs` and `unit_shipping_cost`, never `refund_amount`, `discount_amount`, `processing_fees`, or `allocated_ad_spend` at all. Verified with exact real numbers for SKU `LMP-014` (primary merchant, all 438 real+duplicated line items): `gross_revenue=16,840,000`, `unit_cogs total=32,088,000`, `unit_shipping_cost total=2,292,000`, stored `unit_net_margin total=-17,750,500` (the small residual gap versus a naive `price-cogs-shipping` recompute of `-17,540,000` is explained by E4-1's hidden, unrecorded return-cost deduction, not by any of the 5 leak_breakdown fields). `leak_breakdown` for this SKU showed `returns_cost=1,120,000` as the largest of its 5 displayed values, and the endpoint accordingly set `primary_leak_driver="returns_cost"` — but `refund_amount` is not a term in `unit_net_margin`'s formula at all, so it had **zero actual effect** on why this SKU's margin is negative. The true dominant cost, `unit_cogs` (32,088,000 — roughly 93% of this SKU's total real costs), is not represented anywhere in `leak_breakdown` and can never be selected as `primary_leak_driver`.
- **Severity:** High
- **Impact:** `primary_leak_driver` is a headline, decision-oriented field (intended to tell a merchant *why* a SKU is losing money) but is disconnected from the actual margin formula for 4 of its 5 possible values (`returns_cost`, `discount_cost`, `processing_fees`, `ad_spend` — none of which factor into `unit_net_margin` at all) and can never correctly attribute a leak to COGS, which — per this real dataset — is overwhelmingly the actual dominant driver. A merchant acting on this field's guidance (e.g., "investigate returns_cost") would be investigating the wrong cause.
- **Root cause:** `leak_breakdown`'s 5 components were chosen to mirror the *order-level* `net_margin` formula (`compute_net_margin`'s full parameter list, which does include `refund_amount`/`discount_amount`/`processing_fees`/`allocated_ad_spend`), but the margin value actually being explained here is the *item-level* `unit_net_margin`, which was computed with a narrower parameter set (only `cogs`/`shipping_cost`/`return_cost`, per E2-1's own finding) — the two formulas were never reconciled, and COGS was never added to `leak_breakdown` at all despite being part of both formulas.
- **Suggested fix:** Add a `cogs` component to `leak_breakdown` (using `item.unit_cogs * quantity`), and either remove `returns_cost`/`discount_cost`/`processing_fees`/`ad_spend` from the item-level breakdown (since they don't affect `unit_net_margin`) or fix E2-1/align the two margin formulas so the breakdown's components genuinely sum to the displayed margin gap.
- **Blocks Prompt 5:** No — `total_leaking_skus`/`total_margin_at_risk` themselves are computed consistently (confirmed via exact match to independent recomputation); only the `leak_breakdown`/`primary_leak_driver` explanatory fields are misleading.

## Newly Discovered Ecommerce Prompt 6 issues (AI Layer Testing)

### Issue E6-1: AIRecommendation.currency is fabricated for every Ecommerce recommendation — the context passed to Gemini contains no currency information at all
- **Description:** The `AIRecommendation` schema (shared, `app/schemas/recommendation.py`) requires a `currency` field. Every one of the primary merchant's 8 real, Gemini-generated recommendations set `currency: "USD"` — despite this merchant's real underlying data being 100% NGN-denominated (confirmed throughout Prompts 1-5: `original_currency='NGN'` for every order). Confirmed via reading `get_ecommerce_playbook_response`'s context-building code (`ecommerce_playbook.py:30-40`) and the output shapes of `compute_profit_leaks`/`compute_dead_stock`/`compute_inventory_forecast` (Prompts 4-5): none of `profit_leaks`, `dead_stock`, or `inventory_forecast` include a `currency` key anywhere — the model has zero grounding information to determine the real currency and fabricates a plausible-sounding constant every time.
- **Severity:** Medium
- **Impact:** Every dollar figure in every Ecommerce AI recommendation is mislabeled — a lender, merchant, or downstream system trusting `currency: "USD"` would misinterpret NGN amounts (e.g. 17,750,500) as a US-dollar figure roughly 1000x larger in real terms than intended.
- **Root cause:** The context dicts passed to `generate_recommendations("ecommerce", context)` never include the merchant's real `original_currency` (readily available on every `Order` row, just never threaded into any of the 3 diagnostic/predictive computation functions' output shapes).
- **Suggested fix:** Add the merchant's real currency (e.g. from any real order's `original_currency`, or `MerchantSettings.base_currency` if configured) to the context dict, and/or have the caller override the AI's `currency` field with the real value after parsing, rather than trusting the model to infer or guess it.
- **Blocks Prompt 7:** No.

### Issue E6-2: AIRecommendation.created_at is fabricated for every Ecommerce recommendation (same pattern already confirmed cross-vertical in Bank Prompt 6's B6-3)
- **Description:** Every one of the primary merchant's 8 real recommendations shows `created_at: "2023-10-27T10:00:00Z"` — a plausible-looking but entirely fabricated timestamp, not the real test-execution date. - **Severity:** Low
- **Impact:** No active consequence today (nothing reads/relies on `created_at` as a trust signal in the Ecommerce vertical either), but the same latent trust gap already documented for Bank.

- **Suggested fix:** Same as B6-3 — have the caller overwrite `created_at` with the real timestamp server-side after parsing, rather than trusting the LLM.
- **Blocks Prompt 7:** No.

### Issue E6-3: A real Gemini 429 (rate-limit) error was encountered and is not retried, despite being a case where retrying would likely succeed
- **Description:** A direct, real call to `generate_recommendations("ecommerce", context)` for the Olist merchant failed with `Gemini API client error: Client error '429 Too Many Requests'` (reproduced twice, consecutively, in this same testing session). Per `ai_client.py`'s own design (`if exc.response.status_code < 500: raise GeminiAPIError(...)` — confirmed via code reading, consistent with the Bank engagement's earlier finding): any 4xx status, including 429, is treated as a non-retryable "client error" and fails immediately with **zero retry attempts**, on the stated rationale that "retrying won't help" for client errors. This rationale is accurate for genuine 400/401/403/404 errors, but 429 specifically signals a *transient* condition (a rate limit that a short backoff would very likely clear) — the opposite of "retrying won't help."
- **Severity:** Medium (a real, reproduced reliability gap in a shared module, not Ecommerce-specific — but first observed/reproduced during this Ecommerce testing session)
- **Impact:** Confirmed the failure **degrades gracefully** — `generate_recommendations` caught the `GeminiAPIError` and returned `[]`, so the endpoint still responded `success: true, data: {recommendations: []}` rather than crashing or returning a 500 (a positive confirmation of the fallback design) — but a merchant hitting a transient rate limit gets a silently empty recommendation set with no indication that a retry moments later would likely have succeeded.
- **Root cause:** `generate_text`'s status-code-based retry classification (`app/services/ai_client.py`) groups all 4xx codes together; 429 is architecturally distinct from the other 4xx cases it's grouped with.
- **Suggested fix:** Treat HTTP 429 as retryable (with backoff, same as the existing 5xx/timeout path) rather than grouping it with genuine client errors.
- **Blocks Prompt 7:** No — this is a shared-module finding relevant beyond Ecommerce; not blocking for this vertical's own QA conclusion.
